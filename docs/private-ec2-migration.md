# FRY-59: private EC2 development copy

The personal server remains online and unchanged. This is a second, private copy
of the deployed Flask/SQLite/Waitress application, not a public website cutover.
The source snapshot includes its actual deployed code, consistent SQLite backup
and signing key. Credentials and collaborator names are supplied outside Git/Jira.

## Proposed resources and costs

One Amazon Linux 2023 ARM64 **t4g.micro** in Northern Virginia, 2 vCPUs / 1 GiB
RAM, 8 GiB encrypted gp3 root disk, standard CPU credits (no surplus-credit
charges), and a stable outbound IPv4 address for the restricted Google key.
No load balancer, NAT gateway, paid AMI, Windows licence or interface endpoints.

At the console's $0.0084 Linux hourly rate, 730 hours is about $6.13. At
$0.08/GiB-month, storage is about $0.64. At $0.005/hour, the stable address is
about $3.65. Total base infrastructure is about **$10.42/month running all month**,
before taxes, data transfer and Google API usage. Stopping compute leaves about
**$4.29/month** for the disk and retained address. An AWS budget alert is not a
hard spending cap. Free-tier credits are not assumed.

Sources: [IPv4 pricing](https://aws.amazon.com/vpc/pricing/),
[EBS pricing](https://aws.amazon.com/ebs/pricing/), and the signed-in EC2 console's
instance-type quote. Prices and regional availability must be checked at launch.

## Private access boundary

The security group has **zero inbound rules**. The web service listens only on
`127.0.0.1:8000`. The IPv4 address is for outbound updates, SSM and Google lookup;
it does not make the website public. IMDSv2 is required; no SSH key is provisioned.

Two individual identities get full Linux sudo administration, SSM access and
start/stop/reboot of this instance. They cannot grant IAM permissions, delete
the instance, administer billing or manage unrelated resources. Run As tags map
each identity to its own Linux account. A custom session document avoids changing
account-wide SSM preferences. Console temporary passwords are generated by AWS
and must be changed at first sign-in; no permanent shared password or access key
is created. Each person completes their own password choice.

For local development, the AWS `SignInLocalDevelopmentAccess` policy enables
short-term browser sign-in through `aws login`; it does not widen the underlying
Fry permissions. Install Amazon's AWS CLI v2 and official Session Manager plugin.
The Windows plugin can run from its official package without a system-wide
installation. See [AWS CLI sign-in](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html)
and [SSM port forwarding](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-working-with-sessions-start.html).

After first sign-in, use a separate named CLI profile. Run `aws login --profile
fry-dev --region us-east-1`, then run `tools/Connect-Fry.ps1` with the instance ID,
profile and optional portable-plugin directory. Choose `Shell`, `Website`,
`Start` or `Stop`. Website mode forwards EC2 port 8000 to `http://localhost:8002`.
Closing the session removes that viewing path; nothing is published publicly.

## Migration and validation

1. Render `python tools/render_private_ec2.py`; validate with CloudFormation.
2. Prepare a change set with existing VPC/subnet and separate collaborator-name
   parameters. Review permissions/costs before execution.
3. Back up the personal server with SQLite's consistent backup API; check
   integrity, foreign keys, deployment revision and core table counts.
4. Bootstrap a transfer key **on EC2**. Export only its public certificate.
   Encrypt the transfer archive with CMS/AES-256 to that certificate before
   uploading it. Plaintext database/signing/API secrets must not enter SSM
   command text, command output, Git, Jira or change-set parameters.
5. Configure a separate Places-only Google key restricted to the new outbound
   IPv4 address. Preserve the existing personal-server key and restrictions.
6. Deliver the encrypted archive, run `tools/install_private_ec2.py` on EC2, and
   verify source revision, counts, integrity, loopback listener and private
   homepage/search/details. Check normal and denied IAM permissions for both
   identities and their Linux sudo paths. Complete human first-sign-in separately.
7. Verify anonymous/public connection failure and authenticated forwarding.
   Record acceptance and reviewed PR status before marking Jira Done.

Rollback for the first migration is to continue using the unchanged personal
server. Subsequent EC2 app releases keep the prior release directory: stop the
service, restore the previous `current` symlink and its backed-up state, then
restart and check health. Never copy an older database over newer reviews
without first preserving the current database. Back up EC2 before retiring the
stack; deleting the stack deletes its root disk and releases its address.
